## 1. 版本定位

本版本不含任何产品功能或缺陷修复，全部投入于一件事：**建立可复现、可判定、可解释的性能回归防线**（`pnpm run benchmark`）。

在此之前，「这次改动有没有把性能改坏」无法在 CI 阶段被客观回答，具体卡在三处：

1. **无基线**——性能只能靠人工感受，回归只能等用户反馈（v3.1.0 的 #212 就是这样暴露的：120Hz 用户实测掉帧，而 60Hz 环境下不易察觉）。
2. **有阈值也判不准**——共享 CI runner 上同一份代码的跨运行漂移极大。实测（5 次同代码运行的聚合值）：

   | 指标（场景） | 基线 | 跨运行 σ | 3σ | 3σ 占基线 |
   |---|---|---|---|---|
   | `inputSyncMs`（input-S-rich） | 1.9ms | 0.42 | **1.25ms** | 66% |
   | `saveMs`（save-S-rich） | 53.4ms | 10.8 | 32.5ms | 61% |
   | `longTaskMs`（open-S-rich） | 302ms | 53.6 | 161ms | 53% |
   | `ttiMs`（open-S-rich） | 888ms | 80.4 | 241ms | 27% |
   | `frameMs.p95`（scroll-S-rich） | 17.1ms | 0.13 | **0.39ms** | 2.3% |

   15% 这类固定百分比阈值本身就低于多数指标的噪声——用它判定必然产出一批假 FAIL（开发过程中实测到同一份代码被连续判 5 次"回归"）。
3. **漏检**——只看中位数会漏掉「每 10 帧一次 40ms 尖刺」这类周期性卡顿；只有尾部指标（p95）能捕获。

因此本版本的设计目标不是"调出一个能用的阈值"，而是**让阈值由环境自身的数据决定**，并把"哪些差异根本分辨不出来"如实报告出来。

## 2. 测量层

### 2.1 场景、档位与负载

- **6 个场景**：打开（首帧可交互）/ 连续输入 / 滚动 / 编辑内查找（Ctrl+F）/ 标签切换 / 保存。
- **4 个档位**：S=1k 行、M=5k 行、L=2 万行、XL=5 万行；`quick`（S+M，16 个组合，约 2.5 分钟）/ `full`（+L）/ `xl`（+XL，仅本地）。
- **生成 fixture 按真实压测负载设计**：每 10 节一个 Mermaid 块（本项目最重的渲染元素）、每 5 节一张真实可解码图片；并为 `open` / `scroll` 提供纯文本对照，用于区分"结构本身重"与"渲染元素重"。
- **采样轮数**（不含 warmup 1 轮）：quick=2、full=3、xl=3，`PERF_REPEAT` 可覆盖。quick 从 1 提到 2 的原因：`rounds=1` 时每个标量只有一个样本、没有任何平均，噪声直接顶到阈值上。
- 运行时是 **Playwright chromium + vite dev server（未压缩、含 HMR）**，绝对值不代表生产构建；测量值只用于**同环境纵向对比**（基线按 env/profile/mode/rounds 隔离，本地数与 CI 数永不互比）。真机 WebView2 / WKWebView 表现仍需发版前人工验证。

### 2.2 指标

- **样本型**（每个事件一个样本，取 median 与 p95 两行参与判定）：`ttiMs`、`inputPaintMs`、`inputSyncMs`、`frameMs`、`switchMs`、`searchMs`、`saveMs`。
- **派生标量**：`longTaskMs`、`longTaskCount`、`longFrameCount`、`jankCount`、`jankRatePct`、`cls`、`heapDeltaMB`。
- 两个输入指标刻意互补：`inputSyncMs`（≈1.9ms，纯 JS 同步开销，无 vsync 量化，对亚帧级回归最敏感）与 `inputPaintMs`（≈17ms，含等待下一帧，被 vsync 量化到 16.7ms 的整数倍，但能捕获布局/绘制侧回归）。
- 每次采样把原始数据落到 `.perf-output/raw/<场景>.json`（含 `mode` 与 `absoluteEligible`），**判定可事后独立复算**，不会因执行环境变化而翻转结论。

### 2.3 高刷与真机口径（定向模式）

headless chromium 的渲染锁在 60Hz（帧间隔地板 ~16.7ms），**测不出 120fps 目标**。因此：

- `PERF_HEADED=1`（vsync 跟随显示器）/ `PERF_UNCAPPED=1`（解除帧率上限，帧间隔反映单帧真实工作耗时）/ `PERF_FRAME_BUDGET_MS`（帧预算，默认 16.7）/ `PERF_DOC_FILE`（自备压测文档，只跑这一份）。

## 3. 判定层

### 3.1 三条并行的判定线

| 线 | 比较对象 | 作用 |
|---|---|---|
| 相对 | 本次采样 vs **基线历史** | 回答"有没有比最近几次更差" |
| 绝对 | 本次采样 vs **帧预算硬目标** | 首次运行也能回答"这台机器达没达到目标" |
| 复现 | 首轮 vs 复测轮 | 回答"这个差异是不是抖动" |

### 3.2 噪声门槛：基线历史 3σ

- 基线（schemaVersion 2）为每个指标保留最近 **8 次运行**的聚合值（`history` / `historyP95`）。
- **比较参考值 = 历史中位数**（滚动参考），不再依赖单次运行的偶然快慢——实测 5 次同代码运行的聚合值整体偏移达 −8%~−25%，单点参考会把整批指标一起判成"改善/恶化"。
- **门槛 = 3σ**（由历史估计）。变化未超过 3σ 时**不判 FAIL**，而是 WARN 并标注「变化在运行噪声内（3σ=…）」——确实动了，但幅度不可行动。
- 历史不足 3 次运行时门槛不启用，报告头部**显式说明**并回退到「百分比 + 绝对地板」。
- 为什么用"跨运行历史"而不是"提升 rounds 测运行内 σ"：实测**运行内**两轮的中位数只差 0.10ms，而**跨运行**极差 1.00ms（10 倍）——主噪声在运行之间，运行内 σ 无论提多少轮数都解释不了跨 run 偏移。因此 rounds 维持 2（运行内精度已非瓶颈）。

### 3.3 判定分层与主指标佐证

只有**主指标**（`ttiMs` / `frameMs` / `switchMs` / `searchMs` / `saveMs` / `inputSyncMs` / `inputPaintMs`，含其 `.p95`）可以单独判 FAIL；**派生指标**（`longTaskMs` / `longTaskCount` / `jankRatePct` / `cls` / `heapDeltaMB` 及未登记的新指标）需要**同场景内有主指标同样超阈值**才判 FAIL，否则 WARN 并标注「派生指标无主指标佐证（疑似运行抖动）」。

依据：真正影响用户可感知耗时的退化必然会体现在主指标上；反过来，主指标全绿而只有派生标量涨 35% 的情形在同一份代码上被反复观测到。新增指标想获得"单独判 FAIL"的能力，必须显式登记进 `PRIMARY_METRICS`——"能单独判 FAIL"是一种需要论证的特权。

小量级指标另有**实测绝对地板**（需同时满足相对阈值与地板）：`inputSyncMs` Δ≥1ms、`saveMs` Δ≥8ms、`longTaskMs` {+50% 且 +100ms}、`longTaskCount` {+20% 且 +5} 等；`.p95` 行继承基础指标的地板。所有地板的实测依据写在 `tests/perf/judgment.js` 的 `METRIC_RULES` 注释里。

### 3.4 两阶段复现与退出码

首轮超阈值 → **只复测该场景**（不是全量重跑）→ 仍超阈值判 FAIL，回落判 WARN。只有"可行动"的超阈值才触发复测（被地板/噪声挡下的行不复测，不为抖动多跑一轮）。

退出码：`0` 跑完且无确认回归（含仅 WARN、首次运行无基线）/ `1` 回归复现 / `2` 没测到（infra 故障，先修测量链路，别当成"没回归"）。

控制台摘要按**成因分组**输出 WARN（复测回落 / 未复测 / 无主指标佐证 / 运行噪声内 / 低于绝对地板），避免"把所有 WARN 说成复测回落"这类失真。

### 3.5 绝对目标（帧预算）

滚动场景：帧间隔 p95 ≤ `2 × 帧预算`，掉帧率 ≤ 10%（`PERF_JANK_RATE_LIMIT` 可调）。**只在定向模式（headed/uncapped）产出**——headless 下 vsync 锁 60Hz，帧间隔反映显示器节拍而非单帧工作耗时，判定衡量的是"这台机器此刻忙不忙"而不是代码质量。判定资格随采样落盘（`absoluteEligible`），`PERF_ABSOLUTE=1/0` 可双向强制覆盖。

## 4. 基线层

### 4.1 基线身份 = 测量配置（路径即配置）

```
.perf-baseline/[local/]<profile>/<mode>/r<rounds>/<id>.json
  .perf-baseline/quick/headless/r2/open-S-rich.json          ← CI 日常
  .perf-baseline/local/quick/uncapped/r2/open-S-rich.json    ← 本机 120fps 定向验证
```

- 不同 `mode`（headless / headed / uncapped）与不同轮数**各自维护基线、互不覆盖**——「headless 日常回归」与「uncapped 定向验证」之间来回切不会破坏另一侧（早期两种模式的样本会被混进同一条历史，σ 被污染后真实回归反而被判成"运行噪声内"）。
- **fixture（被测对象）不进路径**：换文档 = 同一路径重建历史（等价于重建基线），并在控制台打印 `基线历史重新起头（id）：FIXTURE_CHANGED`。
- 可比性校验仍覆盖 **env / profile / mode / rounds / fixture** 五维，作用是**不变量守卫**：前四维已由路径保证，若仍不匹配说明基线文件被手工搬动或路径方案变了；真正会命中重建的是 fixture。

### 4.2 历史累积

- 每次 `--update-baseline`（本地或 CI 的 `update_baseline` 勾选）追加一次运行的聚合值，上限 8 点，仅同 fixture 累积。
- 历史累积的可比性判定**与比较侧同一套规则**（直接复用 `baselineComparability`），不做第二份实现。
- 旧 schemaVersion 基线（无历史序列）从本次重新起头，不会把同一个点重复计入。

### 4.3 迁移

本版本把 16 份已提交的 CI 基线从 `.perf-baseline/quick/*.json` 迁移到
`.perf-baseline/quick/headless/r2/`（git 识别为 100% rename）；CI 跑的是 headless/quick/r2，与迁移后路径一致，回归点已由实跑确认（16 个场景全部命中基线，无「未做相对比较」）。

## 5. 工程与 CI

### 5.1 模块边界（三处语义一致）

| 模块 | 职责 | 关键不变量 |
|---|---|---|
| `tests/perf/judgment.js` | **怎么判**：阈值规则、分层、佐证、噪声门槛 | 阈值必须高于该指标的实测噪声地板 |
| `tests/perf/comparability.js` | **能不能比**：env/profile/mode/rounds/fixture 五维 | 混比得到的差值不是性能变化 |
| `tests/perf/report.mjs#baselinePath` | **基线归谁**：身份 = 测量配置，校验 = fixture | 不同配置不共享基线 |

三者都是纯模块，单测直接断言**线上实现**而非其副本。

### 5.2 CI

新增 `.github/workflows/benchmark.yml`：PR 触发，按 quick 档跑 16 个组合，**不阻断合并**，上传 `.perf-output/` 与 `.perf-baseline/` 产物（`include-hidden-files: true`，否则点开头目录会被跳过）并写入 Job Summary；`update_baseline` 手动触发用于重建基线。

### 5.3 测试与变异验证

- 单测从 760 例增至 **840 例**（123 文件），其中 perf 相关 6 个文件：判定策略、可比性矩阵、绝对判定资格、绝对失败路径端到端、基线历史累积、CLI 参数映射。
- 两个端到端测试用**子进程真实调用 `report.mjs`** 跑完整两阶段流转，断言打在**编排交接点**（如 check 阶段的 `retest.json` 内容），而不是只看终态输出——早期人工验证"直接摆好 raw-retest 文件"正是绕过了这一环，导致一条断链在评审中存活。
- 每个修复均带**变异验证**（临时改坏被测行为 → 确认新测试失败 → 还原），举证示例：
  - 还原绝对行复测豁免 → `expected [] to include 'scroll-E-absolute'`（check 阶段清单为空）；
  - `NOISE_SIGMA` 置 0 → 2 例失败；
  - 基线路径退回扁平 → `expected [ 'local/quick/scroll-H-test.json' ] to deeply equal [ Array(1) ]`（两种模式被折叠成一份）。
- 端到端测试的隔离标准集中在 `tests/unit/perf-report-env.ts`（四个可重定向目录一次性全指向临时目录），并附**护栏** `assertRepoBaselineUntouched()`：用例前后比对真实 `.perf-baseline/` 的递归快照，把"忘了重定向"从静默污染变成显式失败。

## 6. 版本范围与门禁汇总

- 代码范围：`git diff --stat v3.1.0..main` 共 50 文件（+6324 / −2，不含发版文档提交）；`src/`、`src-tauri/` 零改动，本版本不改变产品行为。
- 质量门禁：Vitest 123 文件 / 840 用例、Playwright E2E 171 用例、Rust `cargo test` 59 用例（Windows；ubuntu 55，4 个 `#[cfg(windows)]` 用例不参与编译）、`tsc --noEmit` 零错误、CI 双平台（windows-latest / ubuntu-latest）全绿、release 产物覆盖 EXE / MSI / 便携 ZIP / AppImage / deb。
- 本机 Rust 说明：`cargo test` 在本机为 **56 通过 + 3 失败**，失败的 3 例（`cross_device_copy_rejects_symlink_source` / `cross_device_copy_rejects_directory_containing_symlink` / `same_volume_rename_moves_symlink_itself_not_its_target`）是**本机未开启 Windows 开发者模式**所致——`std::os::windows::fs::symlink_file()` 返回 `Ok` 但文件实际未创建，测试的 `is_ok()` 守卫因此失效；CI（Windows runner 具备符号链接能力）为 59/59 全绿，非代码问题。
- 使用入口：`pnpm run benchmark`（本机端口冲突时 `PERF_PORT=3000`），判定与基线维护细则见 `CONTRIBUTING.md` 的「性能 Benchmark」章节。
