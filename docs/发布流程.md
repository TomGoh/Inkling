# 发版流程

> 本文档是发版流程的**仓库内版本**，随 clone 一起走，任何人都能照着执行。
> 本地 `agent.md` 保留同一流程的完整内部版（另含日常 issue 修复与 PR 评审约定），本文件是它的可公开子集。
> 判定与基线的完整规则见 [`CONTRIBUTING.md` 的「性能 Benchmark」](../CONTRIBUTING.md) 章节。
>
> 发版严格按以下五个阶段顺序执行，**不得跳步、不得合并执行**。

## 一、文档更新阶段

发版前必须同步更新以下 4 份文档，缺一不可：

| 文档 | 路径 | 更新内容 |
| --- | --- | --- |
| 设计文档 | `docs/v<版本号> 设计文档.md` | 本版本设计说明（按版本号新建），按惯例须含「已知边界与未决项」一节 |
| 需求文档 | `docs/Markdown编辑器需求文档.md` | 文档版本号、8.1 已实现功能表、8.2 发布版本 |
| README | `README.md` | 版本记录 |
| 变更日志 | `CHANGELOG.md` | 本版本完整条目 |

- **README 的「版本记录」只保留最新 5 条**，更早历史统一由 `CHANGELOG.md` 承载。加新条目时**必须同时删掉最旧一条**：
  核对 `grep -c "^- \*\*v" README.md` 必须等于 **5**（与上一个发版提交对比也应一致）。
- 若本版包含**其他贡献者**的提交，需在 README 的「贡献者」章节补充其信息（姓名 / GitHub 账号 / 参与内容）。
- 文档里的**计数类声明**（提交数、文件数、PR 数、用例数、"新增 N 条"）要用命令逐个复算后再写。
  尤其「本版合并 PR 数」要以**上一个 tag 的提交时间**为分界线，而不是「上一个 tag 名」。

## 二、版本号更新阶段

文档全部更新完成后，再统一更新版本号。以下位置必须同步，不得遗漏：

| 文件 | 位置 |
| --- | --- |
| `package.json` | `version` 字段 |
| `src-tauri/tauri.conf.json` | `version` 字段 |
| `src-tauri/Cargo.toml` | `[package] version` 字段（`src-tauri/Cargo.lock` 的 `inklingmd` 块随之更新） |
| `README.md` | 版本记录条目 |
| `CHANGELOG.md` | 版本条目标题 |
| `docs/Markdown编辑器需求文档.md` | 文档版本号 |
| `docs/v<版本号> 设计文档.md` | 文件名与文内标题 |

更新后全局搜索旧版本号，确认无残留（历史文档与 CHANGELOG 里的旧版本节属正当引用，不改）。自查：

```bash
node scripts/check-version.mjs --tag=v<版本号>
```

## 三、测试验证阶段

在本地依次执行以下三类测试，**顺序不可颠倒**：

```bash
# a) 单元测试（Vitest：单元 + 组件 + store）
pnpm test

# b) 端到端测试（Playwright，首次需先 pnpm e2e:install）
pnpm e2e

# c) Rust 模块单元测试
cd src-tauri && cargo test
```

- 必须以「所有用例全部通过」为准，**不允许存在任何测试失败**。
- Windows 本机若出现 symlink 相关用例失败，需先确认是否为「开发者模式未开启」导致的环境限制，
  而非代码问题；该情况须在发版记录中**显式说明**（基准：CI 双平台应全绿）。

## 四、GitHub Action 执行阶段

本地测试全部通过后，再触发打包流程：

```bash
git push origin main
# 或打 tag 发布
git tag v<版本号> && git push origin v<版本号>
```

- `Build`（`.github/workflows/build.yml`）由 `main` 推送、`v*` tag、PR 或手动触发，执行双平台
  （Windows / Linux）测试与 Tauri 打包，失败阻断构建，产物发布为 GitHub Release。
  **PR 触发只跑 test job**，打包 job 在 PR 上显式跳过（成本控制，见 #252）。
- tag 运行时先跑 `release-guard`（发版前置校验），两道脚本：
  - `node scripts/check-version.mjs --tag=<tag>` —— 四处版本号一致且与 tag 同名；
  - `node scripts/check-docs-updated.mjs --base=<上一个 tag> --head=HEAD` —— 有代码变更则
    `CHANGELOG.md` / `README.md` / `docs/` 至少一处已更新。
- 打包产物由 `Build` 独立产出，**Benchmark 变红不会拦住发版产物** —— 它是「发版性能信号」，
  不是发版门禁（若要硬门禁，需把 benchmark 并进 `build.yml` 并加入 `release.needs`）。
- 发版时「推 main + 推 tag」（通常相隔几十秒）会同时起 **4 个运行**（Build/Benchmark × main/tag），
  各占独立 runner VM，属正常现象；但发版窗口内**不要**再手动播种（见「五」的并发纪律）。

### 发版验证（tag 运行的 Benchmark）

`push: tags: ["v*"]` 会自动触发 `benchmark.yml`，档位为 **full**（比 PR/main 的 quick 多一个 2 万行档），
并注入 `PERF_REQUIRE_COMPARISON=1`：覆盖不足时直接 `exit 2` 并写明「本次结论不构成性能验证」。
tag 运行关闭 `continue-on-error`，失败会红着报出来。

**推 tag 后必做核对清单（核对完才算发版完成）：**

1. `gh run list --workflow=Benchmark --limit 3` 找到本次 tag 运行（`event=push`、`ref=v<版本号>`）。
2. 看 **`判定覆盖：N/M`** —— **N 必须等于 M**；不等就是「没比出结论」，先补齐基线再重跑，不得算作发版完成。
3. 看 **`判定轮次`** —— 期望 `首轮 ✓　复测 ✓　确认 ✓`。若出现 `UNCONFIRMED`，说明确认轮没能给出可信结论
   → **换 runner 重跑**，不要按「没回归」放行。
4. 看 **`FAIL` 计数** —— 大于 0 说明相对回归复现，必须在汇报中写明并判断是否值得拦截；
   `WARN` 要读成因，被噪声门槛（3σ）或绝对地板挡下的**不是**回归。
5. **汇报发版结果时必须一并给出性能结论**，不得只报「发版成功」。

退出码语义：`0` 跑完且无确认回归（含仅 WARN）；`1` 回归复现；`2` 没测到（infra 故障 / 判定覆盖不足）。
**`exit 2` 优先于 `exit 1`**，出现 2 时先修测量链路或补齐该档位基线，**别当成「没回归」**。

**tag 运行 `exit 2` 时的补跑**（exit 2 是测量链路故障、不是判定失败）——直接在 **tag ref** 上补跑一次
发版级验证（tag ref 让补跑保持发版语义：`PERF_REQUIRE_COMPARISON=1`、无 `continue-on-error` 掩盖）：

```bash
gh workflow run Benchmark --ref v<版本号> -f profile=full
```

补跑后按清单 2–4 重新核对，并把补跑 run 的链接写进发版汇报。**补跑不勾 `update_baseline`** ——
验证性复跑不是播种。

另两条口径：

- 性能绝对值不代表生产构建（CI 无 GPU、vite dev server 未压缩），只能同环境纵向对比。
- **真机 WebView2 / WKWebView 表现仍需发版前人工验证**，CI 不覆盖。

## 五、发版后基线维护

完整规则见 [`CONTRIBUTING.md` 的「基线维护」](../CONTRIBUTING.md) 章节。发版相关要点：

- **节奏**：建议**每次发版后补 1 次播种**，把每套基线补到上限 `HISTORY_MAX = 8` 点
  （σ 由历史估计，相对误差 3 点约 50%、8 点约 27%；满 8 点后新点自动顶掉最旧点）。
  **tag 运行不追加历史**（发版只做比较、不写仓库），所以 σ 变准完全依赖手动播种。
- **两套 CI 基线（各自维护、互不覆盖）**：
  - `.perf-baseline/quick/headless/r2/` —— PR 运行与 main push 用（16 个场景）
  - `.perf-baseline/full/headless/r3/` —— tag 运行（发版验证）用（24 个场景，含 2 万行档）
  - ⚠️ **quick 档也要按发版节奏播种**：发版验证只用 full 档，但 PR 与 main 的每次运行都拿 quick 档判定；
    quick 基线陈旧正是「参考值停留在更快的旧环境、每轮顶出假 FAIL」的温床。
- **播种方式**：在 **tag ref** 上 `workflow_dispatch`，取回产物后**手动提交**（CI 不自动 commit）：

  ```bash
  gh workflow run Benchmark --ref v<版本号> -f profile=<quick|full> -f update_baseline=true
  ```

  单次耗时：quick 约 3–6 分钟、full 约 12–15 分钟。
- ⚠️ **确认真的走了播种分支**：日志会回显 if/else 整段，看到 `--update-baseline=1` 字样**不代表执行了它** ——
  必须确认条件行是 `if [ "true" = "true" ]`。
- ⚠️ **产物名要对**：基线更新发生在**跑到 final 的那个 job**，取决于本次走到第几段：
  - 检出疑似回归（起了复测 job）→ 在 **retest** job 更新 → 取 **`perf-benchmark-<profile>-retest`**；
  - 复测后仍有确认候选（起了 retest2 job）→ 在 **retest2** job 更新 → 取 **`perf-benchmark-<profile>-retest2`**；
  - 无嫌疑 → 在 job1 更新 → 取 `perf-benchmark-<profile>`。

  取错等于本次播种**静默丢失**（下一轮从旧基线继续累积，不报任何错）。每个移交 job 的 Job Summary 都会写明该取哪个。
- ⚠️ **取回后先核对再提交**：抽看基线文件的 `updatedAt` 是否为本次运行时间；产物名取对但时间戳没变 = 该次
  根本没开 `update_baseline`，提交等于白提交。
- ⚠️ **必须串行**：下一轮要在**提交了上一轮产物之后**再触发（并行跑只会各写各的单点）。
  播种也不要与 PR / 发版检查并发 —— 共享 runner 争用会让当次测量整体变慢、被误判成回归。
  该纪律已由流水线强制（#291）：`Benchmark` 用全局 `concurrency` 组串行化**所有**运行
  （`group: benchmark` + `queue: max` + `cancel-in-progress: false`）；重要运行仍建议在安静窗口触发。
- ⚠️ **播种遇 `exit 2`（部分场景未测量）**：已测场景的基线会逐场景照常更新，整轮以 `exit 2` 提示本次播种
  **不完整** —— 先修超时 / 失败，再补一次完整播种，不要把不完整的产物直接当成播种结果。
- **产物 retention 仅 7 天**：播种完成后尽快取回，过期不可恢复。

## 发版检查清单

- [ ] 设计文档 / 需求文档 / README / CHANGELOG 已更新
- [ ] README 版本记录仅保留最新 5 条
- [ ] 本次贡献者信息已补充至 README「贡献者」
- [ ] 所有涉及版本号的文件已同步更新，无残留旧版本号
- [ ] 单元测试全部通过
- [ ] E2E 测试全部通过
- [ ] Rust 模块单元测试全部通过
- [ ] GitHub Action 构建成功（Release 产物齐全）
- [ ] tag 运行的 Benchmark 已核对：**`判定覆盖：N/M` 中 N = M**
- [ ] `FAIL` 计数已读；>0 已在汇报中写明并判断是否拦截（`WARN` 已读成因，噪声 / 地板挡下的不算回归）
- [ ] tag Benchmark 若 `exit 2`（没测到）：已在 tag ref 补跑 full 档（不勾 `update_baseline`），
      补跑的判定覆盖 N=M、`FAIL` 计数已核对，链接已写入发版汇报
- [ ] 发版汇报已**一并给出性能结论**（不得只报「发版成功」）
- [ ] 已按「五、发版后基线维护」完成本次播种：**串行**执行、产物名正确（疑似回归时取 `-retest`）、
      基线 `updatedAt` 已核对为本次运行时间、产物已提交
- [ ] 发现性能下降或测量链路故障时，issue 已创建并优先修复
