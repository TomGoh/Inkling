# v2.3.1 设计文档

> 主题：万行多图文档打开卡顿修复（Mermaid 图表视口懒渲染）。

---

## 背景

用户对比 v2.1.0 与 v2.3.0 反馈：打开万行复杂 Markdown 文档（`md_editor_stress_test.md`，398KB / 约 1.8 万行，含 60 张 Mermaid 图、170 个围栏代码块、455 个行内公式）时，v2.3.0 明显更卡。需要定位是哪个功能引入了性能回退并修复。

## 排查方法与结论

### 1. 核心引擎基准（无差异）

用 git worktree 检出 v2.1.0 与 HEAD，共享 node_modules，跑同构基准测试（headless Milkdown + 与 Editor.tsx 相同的 schema/插件装配，加载完整压测文档）：

| 指标 | v2.1.0 | v2.3.0 |
|---|---|---|
| editor.create() | ~4.0ms | ~3.5ms |
| parse（md → doc） | ~780ms | ~750ms |
| serialize（doc → md） | ~180-205ms | ~185-220ms |

核心引擎两版本无差异，排除 parse/serialize/NodeView 构造路径。

### 2. v2.3.0 新增插件审查（非元凶）

- `markdown-publisher`：已有 150ms 防抖 + idle 跳过守卫（v2.3.0 #31/#34 修复）；打开时基线序列化 ~200ms 一次性开销，占比小。
- `outline-tracker`：标题提取 150ms 防抖，滚动路径 rAF 合并，无长任务。

### 3. Chrome DevTools 长任务剖析（定位元凶）

对两个版本做生产构建，浏览器注入同一压测文档，PerformanceObserver `longtask` 实测：

| 场景 | v2.1.0 | v2.3.0（修复前） |
|---|---|---|
| 打开文档长任务 | ~10s | 6.5~7.4s（49~51 个，最长 2.2s） |
| 打开时预渲染 Mermaid | 60/60 | 60/60 |
| 打字长任务 | 68 个共 5.2s | 3 个共 276ms |

关键发现：

1. **打字路径 v2.3.0 反而大幅更优**（publisher 防抖的功劳），排除"新功能拖慢编辑"的假设。
2. **两版本打开时都同步渲染全部 60 张 Mermaid 图**——`mermaid-view.ts` 在 NodeView 构造函数里 `void render(current.textContent)`，每张图 ~150ms 阻塞主线程，合计 ~9s。该问题自 Mermaid 功能引入（v1.x）起就存在。
3. v2.3.0 体感更差的原因：publisher 基线序列化等一次性开销叠加在同一个冻结窗口里，首屏冻结时间更长。

**结论：不是 v2.3.0 功能回退，而是两版本共有的 Mermaid 全量同步渲染瓶颈；v2.1.0 同样卡，只是用户感知阈值不同。**

## 修复设计

[mermaid-view.ts](../src/components/Editor/mermaid-view.ts)：图表改为 IntersectionObserver 视口懒渲染，与 v1.2.0 代码块懒挂载（`code-block-view.ts`）同模式。

```ts
// 视口懒渲染：io 非空表示尚未首次渲染（进入视口前保持占位容器）。
// IntersectionObserver 不可用（如 jsdom 单测环境）时退回立即渲染。
let io: IntersectionObserver | null = null;
if (typeof IntersectionObserver === "undefined") {
  void render(current.textContent);
} else {
  io = new IntersectionObserver(
    (entries) => {
      if (!entries.some((e) => e.isIntersecting)) return;
      io?.disconnect();
      io = null;
      // 用最新节点内容渲染（视口外内容变更只更新 current，不渲染）
      void render(current.textContent);
    },
    { rootMargin: "300px" }, // 预载边距，滚动到附近时提前渲染
  );
  io.observe(container);
}
```

三个关键点：

1. **预载边距 300px**：滚动到图表附近时提前开始渲染，用户滚到时图表已就绪，无"白屏跳变"感（代码块懒挂载用 200px，图表渲染更重故取更大边距）。
2. **`update` 视口外跳过渲染**：ProseMirror 节点更新（如全文替换、源码模式切换回来）在 `io` 未清空前不触发渲染，只更新 `current` 引用，待进入视口后以最新内容首次渲染。
3. **`destroy` 断开观察**：防止文档关闭后残留回调。

占位容器样式复用现有 `App.css`：`.mermaid-block` 有 padding + border，`.mermaid-render` 有 `min-height: 40px`，未渲染块不塌陷为 0 高度，保证 IntersectionObserver 正常触发与滚动条长度稳定。

## 测试适配

happy-dom 提供的 `IntersectionObserver` 不会触发回调，懒渲染会导致依赖"创建即渲染"的单测失败。[mermaid-render.test.ts](../tests/unit/mermaid-render.test.ts) 与 [mermaid-pan.test.ts](../tests/unit/mermaid-pan.test.ts) 加入与 `code-block-view.test.ts` 相同惯例的 IO stub（`observe` 即回调 `isIntersecting: true`），保持原测试契约不变。

E2E（mermaid.spec.ts）无需改动：插入流程本身在视口内，IO 在插入后一帧内触发；实测 8/8 通过。

## 验证数据（生产构建 + Chrome DevTools）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 打开文档长任务 | 6.5~7.4s（49~51 个，最长 2.2s） | **1.9s（4 个，最长 1.5s）** |
| 打开时预渲染图表 | 60/60 | **0/60** |
| 全文滚动最长单任务 | 2s+ 级冻结 | **179ms** |
| 滚动渲染图表数 | 60（打开时已全渲染） | 17（仅滚过视口的） |
| 视口内图表 | 正常 | 正常（滚到即渲染） |
| 标题输入响应 | — | 1 个 220ms 长任务（防抖后一次大纲/序列化遍历） |

剩余的 ~1.9s 打开长任务为 Milkdown 解析 398KB 文档 + 首屏渲染的固有开销（v2.1.0 相同），与 Mermaid 无关。
